VSET module calculates the vector state produced by a VSET instruction and passes that state to [[vset_queue|VSET Queue]]. It receives the requested `vtype`, AVL value, and VSET control from [[decoder|Decoder]], calculates `VLMAX` and the resulting `VL`, checks whether the requested `VTYPE` is supported, and generates the vector configuration associated with the instruction.

The module separates the newly calculated state from the state maintained by the queue. `vl_d` and `vtype_d` represent the candidate state for the current VSET, while `vl_q` is the current `VL` returned by [[vset_queue|VSET Queue]]. The queue therefore handles the state that must survive commit, exception recovery, and branch misprediction recovery.

## Inputs

| Signal                       | Purpose                                                              |
| ---------------------------- | -------------------------------------------------------------------- |
| `vtype_i`                    | Requested `VTYPE`                                                    |
| `avl_value_i`                | AVL value supplied for the VSET                                      |
| `is_vset_i`                  | Indicates that the current instruction changes vector configuration  |
| `rw_cmd_i`                   | Control for the AVL to `VL` operation                                |
| `write_vset_i`               | Requests insertion of the newly calculated VSET state into the queue |
| `vset_commited_i`            | Indicates that a queued VSET has committed                           |
| `recover_commit_exception_i` | Requests recovery after a commit exception                           |
| `recover_last_misspredict_i` | Requests recovery after a branch misprediction                       |
| `vset_index_misspredict_i`   | Identifies the VSET queue entry associated with the misprediction    |
| `clk_i`                      | Clock                                                                |
| `rstn_i`                     | Active low reset                                                     |

The VSET inputs are provided by [[decoder]]. `vset_module` itself does not decode the instruction opcode. It operates on the already decoded VSET information.

## Outputs

| Signal              | Meaning                                    |
| ------------------- | ------------------------------------------ |
| `vset_index_o`      | Current VSET queue index                   |
| `vnarrow_wide_o`    | Active narrow or wide operation enable     |
| `vl_o`              | Current `VL` held by the VSET queue        |
| `vl_short_o`        | Newly calculated `VL` for the current VSET |
| `sew_o`             | Current SEW                                |
| `vill_o`            | Current illegal VTYPE state                |
| `vma_o`             | Current mask agnostic setting              |
| `vta_o`             | Current tail agnostic setting              |
| `vlmul_o`           | Current LMUL                               |
| `vlmax_o`           | Current VLMAX                              |
| `prev_vtype_o`      | First uncommitted VTYPE                    |
| `full_vset_queue_o` | Indicates that the VSET queue is full      |

## Internal State

| Signal              | Meaning                                               |
| ------------------- | ----------------------------------------------------- |
| `vlmax`             | VLMAX calculated from the requested `VTYPE`           |
| `vl_d`              | Candidate `VL` generated by the current VSET          |
| `vtype_d`           | Candidate VTYPE generated by the current VSET         |
| `vl_q`              | Current `VL` maintained by [[vset_queue\|VSET Queue]] |
| `vnarrow_wide_en_d` | Candidate narrow or wide operation enable             |

The `_d` signals are combinational candidate values. `vl_q` is the queue's current registered state. There is no standalone register in `vset_module` for the vector configuration. The state is maintained by [[vset_queue|VSET Queue]].

## `VTYPE` Fields

The module uses the following fields from `vtype_i`:

| Bits     | Field                   | Meaning                         |
| -------- | ----------------------- | ------------------------------- |
| `[2:0]`  | `LMUL`                  | Vector register grouping        |
| `[5:3]`  | `SEW`                   | Vector element width            |
| `[6]`    | `VTA`                   | Tail policy                     |
| `[7]`    | `VMA`                   | Mask policy                     |
| `[10:8]` | Reserved                | Must be zero                    |
| `[11]`   | `VILL` related encoding | Included in the legality checks |

The requested `vtype_i` is converted into the internal `vtype_d` representation. A legal configuration is stored as a zero extended 12 bit VTYPE, while an illegal configuration produces the internal `VILL` representation.

## VLMAX Calculation

`vlmax` is calculated from `VLEN`, `SEW`, and `LMUL`.

For normal LMUL values:

```text
VLMAX = VLEN / SEW × LMUL
```

The implementation performs this using shifts. `VLEN` is first converted from bits to bytes with `VLEN >> 3`, and the SEW encoding determines the additional shift.

Fractional LMUL encodings receive additional division:

| LMUL encoding             | Additional division |
| ------------------------- | ------------------: |
| `101`                     |                `/8` |
| `110`                     |                `/4` |
| `111`                     |                `/2` |
| Other supported encodings |                None |

Thus the `case` statement at lines 65 to 70 is implementing the relationship between VLEN, SEW, and LMUL rather than calculating each configuration separately.

## `VL` Calculation

`vl_d` is only recalculated when `is_vset_i` is asserted.

For normal AVL handling:

| Condition                  | Result               |
| -------------------------- | -------------------- |
| `AVL <= VLMAX`             | `VL = AVL`           |
| `VLMAX < AVL <= 2 × VLMAX` | `VL = ceil(AVL / 2)` |
| `AVL > 2 × VLMAX`          | `VL = VLMAX`         |

The middle case is implemented as:

```systemverilog
(avl_value_i >> 1) + avl_value_i[0]
```

which produces `ceil(AVL / 2)`.

There is also a special path selected by `rw_cmd_i[2:0] == 3'b111`. In that case the module either keeps the existing `vl_q` or uses `vlmax`, depending on the AVL value supplied by [[decoder]]. This is implementation control for the VSET `x0` form rather than a general AVL rule.

## `VL` Without VSET

When `is_vset_i` is `0`:

```systemverilog
vl_d = vl_q;
```

Therefore a normal instruction does not create a new vector configuration. The candidate state simply retains the current `VL`.

## `VTYPE` Validation

The module initially assumes the requested VTYPE is illegal:

```systemverilog
vtype_d = {1'b1,63'b0};
```

If the VTYPE passes the legality checks, it is replaced with:

```systemverilog
vtype_d = {52'b0, vtype_i};
```

The legality condition checks three main areas:

| Check                    | Condition                                             |
| ------------------------ | ----------------------------------------------------- |
| Reserved bits            | `vtype_i[10:8]` must be zero                          |
| SEW                      | Unsupported SEW encodings are rejected                |
| SEW and LMUL combination | Unsupported fractional LMUL combinations are rejected |

When the VTYPE is illegal:

```text
vtype_d = VILL state
vl_d    = 0
```

So an invalid configuration does not merely produce a separate error flag. The candidate vector state itself is changed to the illegal VTYPE state with `VL = 0`.

## Narrow and Wide Operations

`vnarrow_wide_en_d` is recalculated for a VSET using:

```systemverilog
if (vtype_i[2] || (vl_d <= (vlmax >> 1)))
    vnarrow_wide_en_d = 1'b1;
else
    vnarrow_wide_en_d = 1'b0;
```

The signal is therefore enabled when either the relevant LMUL encoding requires it or the resulting `VL` is at most half of `VLMAX`.

Its exact downstream architectural use is outside this module. The value is stored with the VSET state and later returned as `vnarrow_wide_o`.

## VSET Queue Interface

The calculated state is passed to [[vset_queue|VSET Queue]]:

| Queue input                  | Source                       |
| ---------------------------- | ---------------------------- |
| `vl_i`                       | `vl_d`                       |
| `vtype_i`                    | `vtype_d`                    |
| `vnarrow_wide_en_i`          | `vnarrow_wide_en_d`          |
| `vlmax_i`                    | `vlmax`                      |
| `new_vset_i`                 | `write_vset_i`               |
| `commited_vset_i`            | `vset_commited_i`            |
| `recover_last_committed_i`   | `recover_commit_exception_i` |
| `recover_last_misspredict_i` | `recover_last_misspredict_i` |
| `vset_index_misspredict_i`   | Mispredicted VSET index      |

The queue therefore receives both the newly calculated vector state and the control needed to insert, commit, or recover that state.

## Current State and Candidate State

| Signal       | Represents                           |
| ------------ | ------------------------------------ |
| `vl_d`       | `VL` calculated for the current VSET |
| `vl_q`       | Current `VL` held by the VSET queue  |
| `vl_short_o` | `vl_d` exposed to the decoder        |
| `vl_o`       | `vl_q` exposed as the current `VL`   |

This distinction is important because the decoder needs access to the newly calculated VSET result before that state necessarily becomes the committed current state.

## VSET Instructions

`vset_module` does not decode the three VSET opcodes itself. [[decoder|Decoder]] determines which instruction is present and supplies the corresponding `vtype`, AVL, and control information. The relevant instructions are:

| Instruction | AVL source                     | `VTYPE` source | Relevant decoder behavior                         |
| ----------- | ------------------------------ | -------------- | ------------------------------------------------- |
| `VSETVL`    | `rs1` or special `x0` behavior | `rs2`          | Uses `rs1`, `rs2`, `stall_vset_fence`             |
| `VSETVLI`   | `rs1`                          | Immediate      | Uses `rs1`, immediate, usually `stall_vset_fence` |
| `VSETIVLI`  | Immediate                      | Immediate      | Uses immediate values                             |

The VSET instruction classification is performed in [[decoder]], while the resulting vector configuration is calculated here.

## Outputs from `vset_queue`

The queue returns the active vector configuration:

| Output              | Source from queue             |
| ------------------- | ----------------------------- |
| `sew_o`             | Current SEW                   |
| `vl_o`              | Current `VL`                  |
| `vnarrow_wide_o`    | Current narrow or wide enable |
| `vill_o`            | Current `VILL`                |
| `vma_o`             | Current VMA                   |
| `vta_o`             | Current VTA                   |
| `vlmul_o`           | Current LMUL                  |
| `vlmax_o`           | Current VLMAX                 |
| `prev_vtype_o`      | First uncommitted VTYPE       |
| `full_vset_queue_o` | Queue full status             |
| `vset_index_o`      | Current VSET index            |

`vl_short_o` is different because it comes directly from `vl_d`, not from the queue.

## Working Summary

`vset_module` has two responsibilities.

First, it calculates the result of the current VSET instruction by determining `VLMAX`, deriving `VL` from AVL, validating `VTYPE`, and calculating the narrow or wide enable.

Second, it passes that candidate state to [[vset_queue|VSET Queue]], which maintains vector configuration across speculative execution, commit, and recovery. The important distinction is that `vset_module` calculates the candidate state, while the queue maintains the state history.
