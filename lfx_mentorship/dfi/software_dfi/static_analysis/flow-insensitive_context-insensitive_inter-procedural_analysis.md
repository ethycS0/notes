Flow-Insensitive Context-Insensitive Inter-Procedural Analysis (FICIIPA) is the static analysis engine in Data-Flow Integrity (DFI) responsible for computing reaching definition sets for complex, shared, or dynamically referenced memory operations. While [[flow-sensitive_intra-procedural_analysis|FSIPA]] handles unambiguous local variables, FICIIPA operates across the entire codebase to evaluate global variables, static variables, heap allocations, address-taken local variables, and pointer dereferences.

Core Properties and Analysis Scope Inter-Procedural: Operates across all translation units and function boundaries simultaneously, evaluating global data flow across the entire program. Flow-Insensitive: Ignores statement execution sequence within and across functions. Assignments across the codebase are treated as an unordered collection of operations, meaning any write can potentially precede or follow any read regardless of Control Flow Graph (CFG) ordering. Context-Insensitive: Evaluates function calls without distinguishing between different invocation sites or call stacks. Function operations are merged into a single global model regardless of caller identity. Field-Insensitive: Treats entire compound structures, classes, or unions as single unsegmented memory blocks. Accesses to individual struct fields (e.g., `obj.fieldA` and `obj.fieldB`) map to the same abstract memory entity.
### Pipeline Execution Steps

FICIIPA executes in a multi-pass pipeline over the High-Level Intermediate Representation (HIR) across all source files:

- Step 1: Constraint and Write Metadata Collection The compiler scans the HIR across all translation units to collect global assignment rules and track write instruction IDs. Every assignment involving pointers or address-taken variables is converted into a subset constraint. For example, a pointer copy `p = q` yields the inclusion constraint $pts(p) \supseteq pts(q)$. Simultaneously, the analyzer logs every HIR instruction ID that performs a write to a global variable, static variable, address-taken local variable, or pointer dereference.

- Step 2: Constraint Solving via [[andersens_points-to_analysis|Andersen's Points-To Analysis]] The collected set of subset constraints is passed to [[andersens_points-to_analysis|Andersen's Points-To Analysis]] to resolve points-to sets for all pointers. Starting with initial locations introduced by address-of operations (e.g., `p = &a` inserts $a \in pts(p)$), the analyzer executes fixed-point iteration. It continuously propagates target locations through inclusion constraints until no new targets can be added to any pointer's points-to set. This results in a fully expanded mapping of every pointer variable to its set of possible target memory locations.

- Step 3: Reaching Definition Set Construction Using the solved points-to sets and the logged write instruction metadata, FICIIPA constructs the static reaching definition sets for every complex read (use) instruction: Direct Reads of Globals or Address-Taken Locals: The allowed set consists of all direct write instructions targeting that variable, unified with all write instructions targeting pointer dereferences whose solved points-to set includes that variable. Pointer Dereference Reads (e.g., `*p`): The allowed set consists of all write instructions that modify the pointer variable `p` itself, unified with all write instructions targeting any memory location present in `p`'s solved points-to set.

Soundness and Trade-Offs FICIIPA trades precision for scalability. By ignoring execution order, calling context, and internal structure field boundaries, it produces larger (over-approximated) reaching definition sets than a flow-sensitive analysis would. However, because it guarantees that every possible execution path and write instruction is accounted for, it remains sound (conservative). This guarantees that valid program execution will never be halted by a false positive during runtime checking, while keeping static analysis overhead tractable for large C/C++ codebases.
