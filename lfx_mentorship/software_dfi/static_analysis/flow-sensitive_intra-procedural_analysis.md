Flow-Sensitive Intra-Procedural Analysis (FSIPA) is the static analysis engine in Data-Flow Integrity (DFI) dedicated to computing precise reaching definition sets for unambiguous local memory operations. It operates within the compiler's High-Level Intermediate Representation (HIR) using Static Single Assignment (SSA) form and Control Flow Graph (CFG) traversal to track local data flow without evaluating pointer aliasing or cross-function dependencies.
### Scope and Target Variables

FSIPA strictly targets local, stack-allocated variables whose addresses are never taken (meaning no pointer or `&` operator references their memory locations). Because these variables cannot be modified indirectly through pointer dereferences or external function calls, their state transitions are fully deterministic and visible within the current function body. FSIPA evaluates code strictly within individual function boundaries (intra-procedural scope), isolating analysis per function to maximize speed and precision.
### Flow-Sensitivity and CFG Traversal

FSIPA is flow-sensitive, meaning it strictly respects the execution order of statements along all valid execution paths in the Control Flow Graph (CFG). A write instruction ID is added to a read instruction's reaching definition set only if a valid forward execution path exists from that write to the read without an intervening overwrite. Write instructions that appear sequentially after a read in straight-line code are strictly excluded. For conditional branches (such as `if/else` structures), writes along all active incoming paths reaching the merge point are included. For loops, write instructions executed at the bottom of the loop body reach read instructions at the top of the loop on subsequent iterations via loop back-edges.
### SSA Representation and Graph Tracing

FSIPA utilizes Static Single Assignment (SSA) form in the compiler HIR to track local definitions. In SSA form, every assignment to a local variable creates a unique, versioned variable instance ($x_1, x_2, \dots$), turning every write instruction into an explicit single definition. At control flow merge points, SSA introduces phi-nodes ($\phi$-nodes, e.g., $x_3 = \phi(x_1, x_2)$) to explicitly join divergent reaching definitions from different execution branches. Each read (use) instruction in the HIR directly names the specific SSA variable version it consumes. FSIPA traces these SSA version tags backward through the SSA definition graph and its associated $\phi$-nodes directly to the unique instruction IDs that generated them, constructing exact reaching definition sets without requiring iterative points-to solving.
### Handling Function Arguments, Return Values, and Registers

Function arguments and return values cross function boundaries, making their original definition sites inter-procedural. FSIPA handles these boundaries based on how the compiler allocates and passes data:

* Register Allocation: Arguments and return values passed entirely in CPU registers or compiler temporaries are omitted from DFI instrumentation, as CPU registers are inherently isolated from memory corruption attacks.
* Stack Spills and Boundary Flow: When arguments or return values are passed via stack memory or spilled from registers to stack frames, their definitions cross procedure boundaries. Argument initialization inside the callee creates a local stack definition ID for FSIPA to track locally, while cross-call site reaching definitions linking caller writes to callee reads are resolved via inter-procedural analysis.
### Precision and Performance Impact

FSIPA yields exact, minimal reaching definition sets with zero over-approximation for local scalar variables. Because it avoids solving complex pointer constraints or cross-file call graphs, its computational complexity remains linear relative to individual function size. This allows the DFI static analysis pipeline to process the vast majority of program variables rapidly, isolating expensive alias computations to the secondary inter-procedural engine.
