Static analysis in Data-Flow Integrity (DFI) constructs a compile-time model of all valid data dependencies across a codebase. Its primary objective is to compute reaching definition sets for every memory read instruction and compile a static Data-Flow Graph (DFG). This static DFG acts as the specification during program execution, enabling runtime instrumentation to verify that a read instruction only consumes memory generated by an authorized, statically calculated write instruction.
## Core Terminology

* **Definition (Def):** Any compiler instruction that writes data to a memory location. Each definition in the target binary is assigned a unique integer Definition ID.
* **Use:** Any compiler instruction that reads data from a memory location.
* **Reaching Definition:** A definition instruction $D$ reaches a use instruction $U$ if there exists a valid program execution path from $D$ to $U$ where the memory location modified by $D$ is not overwritten.
* **Static Data-Flow Graph (DFG):** The static lookup structure mapping each Use instruction in the program to its explicit set of allowed Reaching Definition IDs.
## Dual-Engine Partitioning Strategy

Computing precise reaching definitions across an entire C/C++ program is computationally expensive when pointers, aliasing, and cross-file dependencies are involved. To balance analysis performance with precision, static analysis splits program memory into two domains processed by separate engines:

1. **Unambiguous Local Memory:** Processed via [[flow-sensitive_intra-procedural_analysis|Flow-Sensitive Intra-Procedural Analysis]]. This engine handles stack-allocated local variables whose memory addresses are never taken. It operates per function using Control Flow Graph (CFG) traversal and Static Single Assignment (SSA) form to construct exact reaching definition sets.
2. **Ambiguous and Global Memory:** Processed via [[flow-insensitive_context-insensitive_inter-procedural_analysis|Flow-Insensitive Context-Insensitive Inter-Procedural Analysis]]. This engine handles global and static variables, heap memory, address-taken local variables, and pointer dereferences. It operates across the entire codebase using Andersen's points-to analysis, sacrificing control-flow and context precision to maintain scalability.
## Compilation Workflow and IR Transformations

Static analysis operates as a multi-pass process over the High-Level Intermediate Representation (HIR) during compilation:

1. **Identification and Tagging:** The compiler scans the HIR to identify every memory write instruction, assigning each a unique Definition ID.
2. **Reaching Definition Calculation:** The [[flow-sensitive_intra-procedural_analysis|FSIPA]] and [[flow-insensitive_context-insensitive_inter-procedural_analysis|FICIIPA]] engines execute. [[flow-sensitive_intra-procedural_analysis|FSIPA]] evaluates local function IRs, while [[flow-insensitive_context-insensitive_inter-procedural_analysis|FICIIPA]] processes project-wide subset constraints. Their outputs are merged into the final DFG dataset.
3. **IR Instrumentation:** The compiler references the DFG to inject abstract verification primitives directly into the HIR before lowering to target assembly:
* `SETDEF(address, def_id)`: Injected at definition instructions to update runtime metadata corresponding to `address`.
* `CHECKDEF(address, allowed_set_id)`: Injected at use instructions to validate that the runtime tag assigned to `address` resides within the static reaching definition set.
## Soundness and Conservatism

Static analysis must be sound (conservative). A reaching definition set for any given Use must include every Definition ID that could legally write to that memory location across any possible execution path. Omitting a valid definition site from a Use's static set would cause the runtime checker to abort execution during legal execution, creating a false positive. While over-approximating definition sets (including redundant write IDs) slightly broadens the runtime attack surface, it guarantees zero false positives during valid program execution.
